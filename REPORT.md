## Раздел 1: Описание проблемы

### Что такое Race Condition?

Race condition (состояние гонки) — это ситуация, когда несколько транзакций обращаются к базе (таблице) для одновременного чтения/изменения данных, результат работы транзакций зависит от порядка, в котором они обработаются.

**Пример из жизни:**
- Два человека одновременно сделали заказ, когда у них в корзине был один и тот же последний на складе товар. Оба заказали товар, который всего один. 

### Почему READ COMMITTED не защищает от двойной оплаты?

Каждый SELECT делает новый снимок данных на момент своего выполнения. Обе транзакции делают SELECT до того как любая из них успела закоммитить изменения, поэтому обе видят одно и то же состояние и обе решают, что операция разрешена. 

На уровне изоляции READ COMMITTED:
1. Каждая транзакция видит информацию снимка, сделанного в момент своего SELECT
2. Когда две транзакции одновременно выполняют запросы, их исходная информация совпадает
4. В результате каждая транзакция проводит операцию на основе одной и той же информации и обе сохраняют изменения

**Демонстрация проблемы:**

```
Время | Сессия 1                    | Сессия 2
------|----------------------------|---------------------------
t1    | BEGIN                      |
t2    | SELECT status (created)    |
t3    |                            | BEGIN
t4    |                            | SELECT status (created)
t5    | pg_sleep(3)                |
t6    |                            | pg_sleep(3)
t7    | UPDATE status = paid       |
t8    |                            | UPDATE status = paid (ждет)
t9    | COMMIT                     |
t10   |                            | UPDATE выполняется...
t11   |                            | COMMIT
```

1. Начало первой транзакции
2. Первый SELECT -> информация для первой сессии зафиксировалась
3. Начало второй транзакции
4. Второй SELECT -> информация для второй сессии зафиксировалась
5. ожидание
6. ожидание
7. Первая транзакция проводит оплату
8. Вторая транзакция проводит оплату (ждет до окончания обновления первой - две транзакции физически не могут записывать информацию в одну строку)
9. Первая транзакция изменила БД и сохранила изменения
10. Вторая транзакция снова перезаписала строку
11. Вторая транзакция изменила БД и сохранила изменения
    
### Примеры из реальной жизни

1. **Двойной клик на кнопку "Оплатить"**
   - Пользователь нажимает кнопку дважды
   - Два HTTP-запроса приходят почти одновременно
   - Оба запроса начинают обработку параллельно

2. **Микросервисная архитектура**
   - Два микросервиса одновременно получили событие "создание заказа"
   - Оба пытаются изменить статус "created" --> "paid"
   - Заказ оплачивается дважды

3. **Сбой сети**
   - Человек дважды нажал на кнопку оплаты -> сайт долго прогружался
   - Человек второй раз нажал на кнопку оплаты -> оба запроса ушли
   - Оба запроса начинают обрабатываться
   - После обработки -> двойная оплата

## Раздел 2: Уровни изоляции в PostgreSQL

### READ UNCOMMITTED

Каждая транзакция видит всю информацию других и доверяет этим данным.

**Предотвращает:**
- Ничего 

**Не предотвращает:**
- Dirty reads
- Non-repeatable reads
- Phantom reads

**Когда использовать:**

Примерно подсчитать сколько заказов сейчас в обработке

**Особенность в PostgreSQL:**

В PostgreSQL READ UNCOMMITTED работает как READ COMMITTED из-за архитектуры MVCC.

---

### READ COMMITTED (по умолчанию)

**Описание:**

Каждая транзакция видит только сохраненную информацию из других транзакций.

Каждый SELECT в транзакции видит новый снимок данных на момент своего выполнения, поэтому два SELECT могут вернуть разную информацию

**Предотвращает:**
- ✅ Dirty reads (чтение незакоммиченных данных)

**Не предотвращает:**
- ❌ Non-repeatable reads (повторное чтение дает другой результат)
- ❌ Phantom reads (новые строки появляются в результате запроса)

**Пример non-repeatable read:**
```sql
-- Сессия 1
BEGIN;
SELECT balance FROM accounts WHERE id = 1; -- Результат: 1000
-- Сессия 2 изменяет balance и делает COMMIT
SELECT balance FROM accounts WHERE id = 1; -- Результат: 500 (!)
COMMIT;
```

**Когда использовать:**

Когда данные только читаются, никакие решения на основе этих данных не принимаются

### REPEATABLE READ

**Описание:**

Транзакция видит snapshot данных на момент начала SELECT и считает эту информацию верной до момента COMMIT.

**Предотвращает:**
- ✅ Dirty reads
- ✅ Non-repeatable reads
- ✅ Phantom reads (в PostgreSQL благодаря MVCC)

**Не предотвращает:**
- ❌ Write skew (специфичная аномалия)
- ❌ Некоторые сериализационные аномалии

**Особенность в PostgreSQL:**
В отличие от стандарта SQL, PostgreSQL на REPEATABLE READ также предотвращает phantom reads.

**Когда использовать:**

Оплата заказа, списание бонусных баллов, бронирование последнего товара на складе. 

### SERIALIZABLE

**Описание:**

Самый строгий уровень, гарантирующий выполнение транзакций в порядке очереди.

**Предотвращает:**
- ✅ Все аномалии чтения
- ✅ Сериализационные аномалии
- ✅ Write skew

**Недостатки:**
- ❌ Может откатывать транзакции при конфликтах (serialization failure)
- ❌ Снижение производительности
- ❌ Требует retry logic в приложении

**Пример serialization failure:**
```sql
-- Сессия 1
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT SUM(balance) FROM accounts; -- 5000
UPDATE accounts SET balance = balance + 100 WHERE id = 1;

-- Сессия 2 (параллельно)
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT SUM(balance) FROM accounts; -- 5000
UPDATE accounts SET balance = balance + 200 WHERE id = 2;

-- При COMMIT одна из транзакций получит ошибку:
-- ERROR: could not serialize access due to read/write dependencies
```

**Когда использовать:**

Везде где есть глобальное правило по всей таблице которое нельзя нарушить
---

### Сравнительная таблица

| Уровень изоляции  | Dirty Read | Non-Repeatable Read | Phantom Read | Performance | Use Case |
|-------------------|------------|---------------------|--------------|-------------|----------|
| READ UNCOMMITTED  | ❌          | ❌                   | ❌            | Высокая     | Аналитика (неточная) |
| READ COMMITTED    | ✅          | ❌                   | ❌            | Высокая     | Обычные операции |
| REPEATABLE READ   | ✅          | ✅                   | ✅*           | Средняя     | Критичные операции |
| SERIALIZABLE      | ✅          | ✅                   | ✅            | Низкая      | Финансовые транзакции |

_*В PostgreSQL REPEATABLE READ также предотвращает phantom reads благодаря MVCC._

## Раздел 3: Решение проблемы

### Почему REPEATABLE READ решает проблему?

REPEATABLE READ использует snapshot isolation:
1. Транзакция видит снимок данных на момент первого SELECT и только его до момента COMMIT
2. Однако REPEATABLE READ сам по себе не решает проблему — UPDATE в PostgreSQL пересчитывает WHERE по актуальным данным, поэтому UPDATE сессии 2 просто затронет 0 строк, но не упадёт с ошибкой
3. Без FOR UPDATE сессия 2 продолжит выполнение и безусловно сделает INSERT в историю — двойная запись всё равно возникнет

Именно поэтому FOR UPDATE обязателен: он блокирует строку с момента SELECT, и когда сессия 2 дожидается снятия блокировки — она видит уже актуальный статус 'paid' и выбрасывает OrderAlreadyPaidError ещё до INSERT.

### Зачем нужен FOR UPDATE?

FOR UPDATE ставит замок на строку в момент SELECT, другие сессии ждут снятия замка. После снятия замка другие сессии видят последние закомиченные данные.

`FOR UPDATE` создает эксклюзивную блокировку на уровне строки (row-level lock):

**Без FOR UPDATE:**
```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT status FROM orders WHERE id = '...';
-- Другая транзакция может прочитать ту же строку
UPDATE orders SET status = 'paid' WHERE id = '...';
COMMIT;
```

**С FOR UPDATE:**
```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT status FROM orders WHERE id = '...' FOR UPDATE;
-- Другая транзакция ЖДЕТ освобождения блокировки
UPDATE orders SET status = 'paid' WHERE id = '...';
COMMIT;
```

**Типы блокировок:**
- `FOR UPDATE` — эксклюзивная блокировка (никто не может изменить или заблокировать)
- `FOR SHARE` — разделяемая блокировка (другие могут читать с FOR SHARE, но не могут изменять)
- `FOR NO KEY UPDATE` — как FOR UPDATE, но разрешает concurrent FOR KEY SHARE
- `FOR KEY SHARE` — слабая блокировка (предотвращает DELETE и UPDATE ключевых полей)

### Что произойдет без FOR UPDATE на REPEATABLE READ?

Без FOR UPDATE обе сессии читают строку одновременно без замка, обе видят "created", обе начинают выполнять бизнес-логику. Ошибка сериализации прилетает только в самом конце — когда сессия 2 уже сделала INSERT в историю и всю остальную работу. Всё это потом откатывается 
---

Даже на REPEATABLE READ возможна аномалия:

```sql
-- Сессия 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT status FROM orders WHERE id = '...'; -- created
-- Задержка...
UPDATE orders SET status = 'paid' WHERE id = '...' AND status = 'created';
COMMIT;

-- Сессия 2 (параллельно)
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT status FROM orders WHERE id = '...'; -- created (snapshot!)
-- Задержка...
UPDATE orders SET status = 'paid' WHERE id = '...' AND status = 'created';
-- ЧТО ПРОИЗОЙДЕТ?
```

Сессия 2 встанет в очередь на UPDATE, потому что сессия 1 уже держит автоматический row-lock на строке.
После того как сессия 1 делает COMMIT — сессия 2 продолжает работу. PostgreSQL пересчитывает WHERE-условие по актуальным данным: status = 'created' уже не выполняется, UPDATE затрагивает 0 строк. Никакой ошибки сериализации нет — сессия 2 продолжает выполнение и безусловно вставляет запись в историю. Итог: двойная оплата.

### Разница между FOR UPDATE и FOR SHARE

| Характеристика | FOR UPDATE | FOR SHARE |
|----------------|------------|-----------|
| Тип блокировки | Эксклюзивная | Разделяемая |
| Блокирует чтение с FOR UPDATE | ✅ | ✅ |
| Блокирует чтение с FOR SHARE | ✅ | ❌ |
| Блокирует UPDATE | ✅ | ✅ |
| Блокирует DELETE | ✅ | ✅ |
| Use case | Перед изменением | Защита от изменений |

**Пример использования FOR SHARE:**
```sql
-- Проверка наличия товара перед созданием заказа
SELECT quantity FROM products WHERE id = '...' FOR SHARE;
-- Товар не может быть удален или изменен до COMMIT
```

## Раздел 4: Рекомендации для продакшена

### Какой ISOLATION LEVEL использовать для продакшена маркетплейса?

**Рекомендация:** Для продакшена маркетплейса рекомендуется использовать **READ COMMITTED как default уровень** с явным использованием **REPEATABLE READ + FOR UPDATE для критичных операций**.

#### Обоснование:

**1. Производительность**
- READ COMMITTED имеет минимальный overhead - каждый запрос просто делает снимок на момент своего SELECT и сразу работает, никаких дополнительных проверок
- REPEATABLE READ используется только там, где необходимо — блокировка ставится только на конкретную строку конкретного заказа, остальные транзакции не затронуты
- Избегаем глобального использования SERIALIZABLE, поскольку при высокой нагрузке он вызывает частые откаты и требует retry logic


**2. Безопасность данных**
- Критичные операции (оплата, изменение баланса) защищены через REPEATABLE READ + FOR UPDATE — строка заблокирована с момента чтения, двойная оплата физически невозможна
- Некритичные операции (просмотр каталога) работают на READ COMMITTED, если цена изменится пока пользователь смотрит каталог, ничего критичного не произойдёт
- Четкое разделение зон ответственности


**3. Риски deadlock**
- FOR UPDATE может привести к deadlock при неправильном порядке блокировок - две транзакции блокируют одни и те же строки в разном порядке и ждут друг друга вечно
- Решение: всегда блокировать ресурсы в одном порядке
- Пример: сначала order, потом order_items, потом payment


**4. Простота разработки**
- READ COMMITTED легко понять и отлаживать
- REPEATABLE READ + FOR UPDATE требует explicit intent - явно обозначаем, что операция критична
- Код становится самодокументируемым
- В отличие от SERIALIZABLE не нужно писать retry logic — REPEATABLE READ + FOR UPDATE либо проходит успешно, либо падает с понятной ошибкой OrderAlreadyPaidError


**5. Масштабируемость**
- READ COMMITTED хорошо масштабируется
- Локальное использование блокировок не создает bottleneck
- Connection pooling работает эффективно
- FOR UPDATE блокирует только конкретную строку заказа, а не всю таблицу — параллельные оплаты разных заказов не мешают друг другу

### Альтернативные подходы

#### Подход 1: Использовать SERIALIZABLE везде

**Плюсы:**
- Максимальная корректность
- Не нужно думать о блокировках
- PostgreSQL автоматически обнаруживает конфликты

**Минусы:**
- Значительное снижение производительности (20-50%)
- Требует retry logic во всех операциях
- Высокий процент rollback при нагрузке
- Сложная отладка serialization failures

**Вывод:** Не рекомендуется для high-load систем.

#### Подход 2: Optimistic Locking (версионирование)

**Реализация:**
```sql
ALTER TABLE orders ADD COLUMN version INTEGER DEFAULT 1;

UPDATE orders 
SET status = 'paid', version = version + 1
WHERE id = '...' AND status = 'created' AND version = 1;

-- Проверить ROW_COUNT, если 0 — конфликт
```

**Плюсы:**
- Нет блокировок на чтение
- Хорошая производительность
- Масштабируется горизонтально

**Минусы:**
- Требует изменения схемы БД
- Требует retry logic в приложении
- Может быть много конфликтов при высокой нагрузке

**Вывод:** Хороший подход для распределенных систем.

#### Подход 3: Advisory Locks

**Реализация:**
```sql
BEGIN;
SELECT pg_advisory_xact_lock(hashtext('order_' || order_id));
-- Критическая секция
COMMIT; -- Блокировка автоматически снимается
```

**Плюсы:**
- Гибкий контроль блокировок
- Можно блокировать логические ресурсы
- Работает на любом уровне изоляции

**Минусы:**
- Легко забыть снять блокировку
- Сложнее отлаживать
- Требует дисциплины от разработчиков

**Вывод:** Полезно для специфичных случаев, но не как основной подход.

### Итоговая рекомендация

Для продакшена маркетплейса используйте **гибридный подход**:

1. **Default isolation level:** `READ COMMITTED`
   - Для обычных операций (чтение каталога, просмотр истории)
   - 95% операций

2. **REPEATABLE READ + FOR UPDATE:** для критичных операций
   - Оплата заказа
   - Изменение баланса
   - Резервирование товара
   - 5% операций

3. **Дополнительно:** Optimistic locking для операций с высокой конкурентностью
   - Обновление счетчиков
   - Изменение рейтингов

**Пример кода:**
```python
async def pay_order(order_id: UUID):
    async with db.transaction(isolation='repeatable_read'):
        # Заблокировать заказ
        order = await db.fetch_one(
            "SELECT * FROM orders WHERE id = $1 FOR UPDATE",
            order_id
        )
        
        if order['status'] != 'created':
            raise OrderAlreadyPaidError()
        
        # Обновить статус
        await db.execute(
            "UPDATE orders SET status = 'paid' WHERE id = $1",
            order_id
        )
        
        # Записать в историю
        await db.execute(
            "INSERT INTO order_status_history (order_id, status) VALUES ($1, 'paid')",
            order_id
        )
```
